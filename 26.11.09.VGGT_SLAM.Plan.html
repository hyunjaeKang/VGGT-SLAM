01추천 결론

VGGT-SLAM은 유지하고,
객체 검출·추적을 별도 상주 worker로 실행합니다.

영상이 들어오면 사람·차·자전거 같은 사전 대상은 즉시 2D로 표시합니다. 같은 프레임의 VGGT 깊이와 최적화가 준비되면 해당 객체를 3D 지도에 올립니다. “깊이가 아직 없음”과 “객체를 못 찾음”을 서로 다른 상태로 보여줍니다.

먼저 발견경량 box/mask 검출 + 2D 추적
CPU SAM3 전수 분할을 기다리지 않음
나중에 3D 확정동일 frame의 depth·confidence와 결합
local anchor로 그래프 보정에 대응
완료 후 정밀화SAM3/큰 모델은 필요한 ROI·새 객체에만
누락 보충과 기존 검색 기능 유지

이것은 조사에 기반한 설계 판단입니다. 새 모델을 이 Mac에서 benchmark한 결과가 아닙니다. 문서 작성 중 V4 구현·환경 업그레이드·모델 다운로드는 하지 않았습니다.

기본 모델 선택

대상이 COCO 클래스에 포함되면: YOLO26n/s-seg와 검증된 YOLO11n-seg 중 실제 Mac 측정이 좋은 모델 → ByteTrack. printer·특정 설비 등 COCO 밖이면: YOLOE-26s/YOLOE-11s의 사전 vocabulary → 가능한 경우 frozen export. 프롬프트 언어·동의어는 시작할 때 정규화합니다. [S05] [S06] [S07]

ROAD/sky는 별도: road는 객체 box 모델에 맡기지 않고 경량 semantic segmentation을 비교합니다. 야외 도로 모델이 해변 모래나 실내 바닥을 road라고 오인하면 off/unknown으로 둡니다. SAM3는 현재 성공 경로를 남겨 정밀 fallback으로 씁니다. [S15] [S03]

디스크 영상 → 방향·PTS 정규화 → frame_uid 부여원본은 보존 / 뷰용 최신 슬롯과 기록용 작업 목록 분리

B · VGGT / 지도키프레임 선택 → 소형 submap → 깊이·신뢰도·카메라 → 그래프 완료 event
map revision마다 확정된 깊이
C · ROAD / 정밀 확인경량 road/sky → 새 객체·불확실 ROI만 정밀 segmentation
예산이 부족하면 정밀화 지연
같은 frame_uid로 결합 → local support 저장 → 최신 H로 3D/BEV에 표시완성된 지도 스냅샷과 detector 관측을 결합 / 임의의 최신 RGB와 과거 깊이를 섞지 않음

대기열 정책이 핵심입니다

  • 표시용: latest-only 1~2슬롯. 늦은 결과로 현재 RGB를 덮지 않습니다. 화면 frame과 mask frame이 다르면 마스크를 숨기고 “지도 기준 시각”을 따로 표시합니다.
  • 실시간 처리: 입력 속도를 따라가기 어려우면 의미 추론 샘플률/이미지 크기를 낮추고 drop·coverage를 기록합니다. 지도를 위한 overlap·앵커 키프레임은 임의 폐기하지 않습니다.
  • 전수 기록: 독립 디스크 작업 목록에서 모든 선택 키프레임을 최종 처리합니다. 처리량이 부족하면 “후처리 중”을 보여줍니다. bounded queue에서 버려놓고 전체 검색 완료라고 하지 않습니다.
  • 최종 전환: map complete / live semantic ready / exhaustive refinement complete를 나눠 표시합니다. ROAD가 끝날 때까지 지도 탐색·이미 얻은 객체 검색까지 막지 않습니다.

2026-10-24 · HorizonStream v2

bounded geometric state와 장기 attention을 다룹니다. 새 streaming geometry 후보이지만 detector/semantic map/기존 loop 기능을 대신하지는 않습니다. 먼저 기존 backend 유지형 V4의 병목을 제거한 뒤 비교합니다. [S27]

2026-10-06 · S2Tok

지속적 spatial tokens를3D Gaussians로 디코딩하는 연구입니다. 재생의 외관 개선과 지도 기하·객체ID 문제는 분리합니다. voxel/점군 backend를 바로 대체하기보다 연구 트랙에 둡니다. [S36]

2026-03-27 · SAM3.1 / 현재 YOLOE-26

2025년 SAM3 한 버전이나 YOLO-World만 비교하는 계획은 충분하지 않습니다. 다중 객체 처리 개선과 더 가벼운 vocabulary detector를 함께 검토합니다. 최신이라고 기존 성공 환경을 바로 업그레이드하지 않습니다. [S04] [S06]

현재 공개 · DARTF, MetricTrail, SceneVGGT

논문/공식 코드 중심41개 핵심 원문을 검토했습니다. 모든 관련 논문을 완전 망라했다고 주장하지 않으며, 검색 요약의 날짜 대신 arXiv 제출/수정일을 확인했습니다. 요청 파일명의11-09를 실제 조사일로 바꾸어 적지 않았습니다.

06틀린 프레임·틀린 좌표·중복 객체를 막는 계약

① 같은 입력임을 먼저 증명

frame_uid = run_id + source_frame_id + orientation/crop identity. 원본 PTS와 정규화 RGB hash를 저장합니다. mask를 native→recorded depth grid로 옮기는 변환, resize/padding/crop/회전을 명시합니다. source frame 번호가 같아도 run 또는 방향·crop이 다르면 같은 마스크 캐시를 쓰지 않습니다.

②3D를 아직 모르면2D 상태 유지

box만 있으면 바로 뒤 배경 깊이를 채워 거대한3D 박스를 만들지 않습니다. foreground mask 또는 검증된 지지점이 생기면 confidence·유한값·깊이 경계로 분리합니다. rank/최소점 검사는 기존 정책을 유지하고, 강건한 quantile/PCA fitting을 비교합니다. road 같은 평면 표면에는 부피가 있는 객체 box를 강제하지 않습니다.

③world box를 영구 저장하지 않음

관측 원본: frame_uid, node_id, local_support, mask_ref, quality
표시 시점: X_world = dehomogenize(H_node(revision) · X_local)
2D 검증:   pixel ≈ project(P_world(revision) · X_world)

loop 최적화 → H 변경 → local support 재투영 → world bounds 재계산
SL(4) 변환을 rigid SE(3)처럼 center/extent에만 적용하지 않음

현재 프로젝트의 depth_display_points와 snapshot의 P@H 계약을 재사용합니다. 새 모델이 camera-local Euclidean depth를 내는 경우에는 별도 어댑터에서 현재 projective map과의 scale/gauge를 검증해야 합니다. 검증 전 metres 단위 gate를 쓰지 않습니다.

④track ID와 고유 객체ID는 다름

ByteTrack ID는 영상의 단기 트랙입니다. 정적 객체는 다중 뷰 지지점·appearance·class·시각·재투영 일관성으로 submap을 넘어 연결합니다. 확신 없으면 연결 보류로 둡니다. 차량·사람처럼 움직이는 대상은 시간별 pose/TTL을 갖고 정적 도로 지도에 영구 융합하지 않습니다. 루프 재방문과 동적 이동을 같은 규칙으로 합치지 않습니다. [S14] [S19] [S20] [S33]

07“부드러운 화면”과 “실시간 계산”의 차이

표시 FPSRGB·3D 화면이 얼마나 자주 그려지는가
30~60Hz는 모델 FPS가 아님
처리량초당 실제 새 검출/깊이 계산 수
지속 입력 속도보다 작으면 대기열 증가
결과 나이입력의 재생 기준 시각과 현재 표시 시각의 차이
늦은 결과는 빠르게 그려도 오래된 정보

초기 Mac 목표는 2D 검출·추적10Hz, p95 결과 나이350ms 이하부터 검증합니다. 새3D는 “서브맵 준비 후 표시”, 초기 후보 목표는 map commit 후 semantic attach p95 500ms 이하와 source 기준3D 결과 나이5초 이하입니다. 이 목표가 안 되면 객체 FPS만 올려 실시간이라고 하지 않고 CUDA worker/geometry adapter를 비교합니다.

시간 측정 계약: 실시간 replay는 presentation_monotonic − (stream_origin_monotonic + PTS상대시간/replay_rate)로 결과 나이를 계산합니다. offline 입력은 result_ready_monotonic − ingest_monotonic의 처리 지연을 따로 보고합니다. wall-clock과 상대 PTS를 직접 빼지 않습니다. 원격 worker는 입력 frame ID를 돌려주고 클라이언트 수신/표시 시각으로 종단 지연을 측정하며 서로 다른 장치의 monotonic clock을 직접 비교하지 않습니다.

아래 숫자는 자유롭게 바꾸는 설계 시뮬레이션 입력이며 로컬 측정표가 아닙니다. 첫 지도는 submap을 채우는 시간까지 필요합니다. UI animation, 모델 로딩, I/O, 동시에 GPU를 쓸 때의 경합은 별도 추가해야 합니다.

공식: geometry 처리량=(총 view−중첩1)/submap시간. 지도 사용률=선택키프레임Hz/처리량. 첫 지도 대기≈(총 view−1)/선택Hz+submap시간. detector 사용률=실행Hz×관측시간. 두 사용률은 각각의 worker 기준이며 공유 GPU/메모리 경합이 없다는 가정입니다.

운영 모드: Live freshness는 샘플·drop·coverage를 공개하고 최신을 우선합니다. Archive completeness는 모든 선택 키프레임을 결국 처리하되 시간이 더 걸릴 수 있습니다. 두 모드를 동시에 제공하되 전수성을 실시간 프레임 보장으로 설명하지 않습니다.

추천 경로의 의사결정

  1. 대상이 고정 클래스 안에 있음: 경량 detector를 먼저 쓴다. open-vocabulary의 비용을 강제하지 않는다.
  2. 새 텍스트 클래스가 필요함: 사전 vocabulary YOLOE. 낮은 recall은 class별 threshold·prompt·해상도를 소량 GT로 비교한다.
  3. mask가 약함: 선택 keyframe에만 SAM3 또는 EdgeTAM으로 보완한다. tracker가 새 객체를 만들 수 없으므로 주기적 재검출은 유지한다.
  4. 3D가 늦음: 상주 worker만으로 해결됐는지 먼저 본다. fill-time/geometry가 지배하면 sampling·짧은 submap·CUDA·새 geometry adapter 순으로 비교한다.
